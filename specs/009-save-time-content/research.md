# Дослідження: 009 Збереження, час і оновлення контенту (етап 1)

10.10.2026. Обсяг — фундамент етапу 1 (`docs/implementation-strategy.md`): збереження, знімки, міграції, час, запуск. Решта FR відкладена з причиною (див. plan.md, «Обсяг»). NEEDS CLARIFICATION немає.

## 1. Сховище

**Рішення.** `react-native-mmkv` 4 (Nitro Module) + `react-native-nitro-modules` через `npx expo install`. Обгортка `KeyValue { getString, set, remove }` у `src/save/storage.ts`; уся логіка збереження приймає `KeyValue` аргументом, тож тести йдуть на пам'ятній реалізації.
**Чому.** Конституція (VIII, технічні обмеження): zustand + MMKV. Синхронне читання на `boot` без промісів. У Jest MMKV мокається автоматично.
**Наслідок.** Expo Go без нативного модуля не підійде: потрібна development build (`eas build --profile development`). Веб-збірка для перевірки в Chromium — через web-реалізацію MMKV (localStorage); якщо її немає, `storage.ts` падає назад на `localStorage` лише на web.
**Альтернативи.** AsyncStorage — асинхронний, повільніший, не за конституцією.

## 2. Цілісність запису (FR-1, FR-3)

**Рішення.** Запис — JSON `{ schemaVersion, savedAt, appVersion, contentVersion, economyConfig, checksum, game }`. `checksum` = FNV-1a 32 біти (hex) від `JSON.stringify` усіх полів, крім `checksum`, у фіксованому порядку. Перевірка на завантаженні: розбір JSON → `schemaVersion` → контрольна сума → zod-схема поточної версії (після міграцій).
**Чому.** Ловить обрізаний запис і випадкову зміну; криптостійкість не потрібна (захист від шахрайства — поза MVP). FNV-1a — 10 рядків, без залежностей.
**Альтернативи.** SHA-256 через expo-crypto — асинхронний і надмірний.

## 3. Схема й міграції (FR-9…FR-11)

**Рішення.** zod 4. `CURRENT_SCHEMA = 1`. `migrations: Record<number, (game: unknown) => unknown>` — чисті функції vN → vN+1; `loadSave()` проганяє ланцюжок, перед міграцією робить знімок (FR-4). Тести інжектують фікстурні міграції (схеми 1 → 3), щоб перевірити AC-7 до появи справжніх.
**Новіша схема** (FR-11): запис не читаємо й не перезаписуємо, `boot` веде на `force-update` з `appVersion` із запису.

## 4. Знімки (FR-4, FR-6)

**Рішення.** `save.bak1` (новіший) і `save.bak2`. Знімок валідного `save` — на початку сесії (холодний старт або повернення після ≥ 120 с) і перед міграцією; `bak1 → bak2`, поточний → `bak1`. «Відновити з копії» бере найновіший валідний, пише його як `save`, офлайн рахується від його `savedAt`.

## 5. Час (FR-12…FR-15)

**Рішення.** Передній план — монотонний годинник (уже в 001: `useGameLoop`). Між сесіями Δ = зараз − `savedAt`. Якщо Δ < 0 (FR-14): чиста функція `shiftTimers(state, effects, Δ)` зсуває всі абсолютні мітки (`fuelEndMs`, `catBonusAtMs`, `tapTimes`, `startMs`/`endMs` ефектів) на Δ, офлайн = 0, `clock-toast`, `is_clock_skew_detected`. Денні ліміти — дата РРРР-ММ-ДД, скидання лише на пізнішу (уже в 001 для ×2; той самий хелпер для решти лімітів, коли вони з'являться).

## 6. Конфіг (FR-22)

**Рішення.** До першої покупки рівня гра бере вбудований `econ-v7.2` (рішення 52); у момент першої доменної події `purchase` конфіг закріплюється в `save.economyConfig` з `source` = bundled. Після завантаження закріплений конфіг має пріоритет над вбудованим (`source` = cached), тож оновлення застосунку криву цін не змінює. Прапор PostHog (FR-21) додасть етап 5 у ту саму точку.

## 7. install_id

**Рішення.** `expo-crypto` `randomUUID()` → MMKV-ключ `install_id` при першому запуску; поза `save` (не чіпається ні пошкодженням, ні скиданням). Подію `app_first_open` надішле етап 5.

## 8. Запуск (FR-28, FR-29)

**Рішення.** `boot` — синхронне читання MMKV, тож зазвичай «коротке». Таймер 1 с перемикає на «довге» з «неписаною істиною» (3 рядки зі специфікації, тап гортає). Маршрут: newer → `force-update`; пошкоджено → `save-error`; є запис і відсутність ≥ 5 хв → `offline-return` (компонент 001); інакше `main`. Онбординг (002) встане між `save-error` і `offline-return`.

## 9. Звіт про збій (FR-8, ВП-9)

**Рішення** (рекомендація ВП-9): `Sentry.captureMessage('save_corrupt')` з тегами `error_code`, `schema_version`, `size_bytes`, `checks` — без тіла запису й позивного. Без DSN — no-op.

## 10. Запис (FR-2)

**Рішення.** Таймер 5 с на передньому плані + AppState `background` + `saveNow()` для покупки в магазині, цифровізації, скидання (виклики додадуть 06, 08, 10). Помилка запису → повтор на наступному тіку (крайовий випадок «місце скінчилося»); подію `app_error_log` надішле етап 5.
